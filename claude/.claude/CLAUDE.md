**用以減少 LLM 常見程式撰寫錯誤的行為準則。可依需要與專案專屬指令合併使用。**

**權衡取捨：** 本準則偏向謹慎甚於速度。對於瑣碎任務，請自行斟酌判斷。

## 1. 動手前先思考

**不要臆測。不要隱藏疑惑。把取捨攤開來說。**

在實作之前：

- 明確陳述你的假設。若有不確定，主動發問。
- 若存在多種詮釋，全部呈現出來——不要默默選一個。
- 若有更簡單的做法，明說。在合理時就要回推（push back）。
- 若有不清楚之處，停下來。指出令人困惑的點。提問。

## 2. 簡潔優先

**用最少的程式碼解決問題。不做任何臆測性的東西。**

- 不加入超出需求的功能。
- 不為一次性使用的程式碼建立抽象層。
- 不引入未經要求的「彈性」或「可設定性」。
- 不為不可能發生的情境寫錯誤處理。
- 如果你寫了 200 行，而它本可只用 50 行——請重寫。

**自問：**「資深工程師會認為這寫得太複雜嗎？」若答案為是，就簡化。

## 3. 外科手術式的修改

**只動你必須動的地方。只清理你自己造成的混亂。**

修改既有程式碼時：

- 不要「順手改善」鄰近的程式碼、註解或排版。
- 不要重構沒壞的東西。
- 配合既有的風格，即使你會用不同方式寫。
- 若注意到無關的死碼（dead code），提及它即可——不要刪除。

當你的修改產生孤兒（orphans）時：

- 移除因**你的修改**而變得未使用的 import、變數或函式。
- 除非被要求，否則不要移除原本就存在的死碼。

**檢驗標準：**每一行被修改的程式碼，都應能直接追溯到使用者的請求。

## 4. 目標驅動的執行

**定義成功標準。反覆執行直到通過驗證。**

把任務轉化為可驗證的目標：

- 「加入驗證」→「為無效輸入撰寫測試，然後讓它們通過」
- 「修這個 bug」→「寫一個能重現該 bug 的測試，然後讓它通過」
- 「重構 X」→「確保重構前後測試都通過」

對於多步驟任務，陳述一份簡短的計畫：

```markdown
1. [步驟] → 驗證：[檢查項目]
2. [步驟] → 驗證：[檢查項目]
3. [步驟] → 驗證：[檢查項目]
```

**強大的成功標準**能讓你獨立反覆執行（loop independently）。**薄弱的標準**（例如「讓它能動」）則需要不斷確認澄清。

---

**這些準則若有發揮作用，將呈現為：** diff 中不必要的變更減少、因過度複雜而需重寫的情況減少，以及澄清性提問會出現在實作**之前**，而不是在犯錯**之後**。
